# PyWebview Driving UI and Driven SharePoint SSO with Single-File Static Astro Frontend

> **Note:** The static Astro frontend choice in this ADR is partially superseded by [ADR-0008](./0008-vite-solidjs-single-file-ui.md) (Vite + SolidJS single-file bundle); `pywebview`, `WebViewDriver`, single-file `src/idat_sync/ui/index.html` packaging, and pure-Python UI controllers remain in effect.

We use `pywebview` on both outer sides of the hexagonal architecture—as the Driving UI adapter in `src/idat_sync/ui/` rendering a build-time-compiled single-file Astro + Tailwind CSS bundle (`src/idat_sync/ui/index.html`) passed directly via `html=...` with zero Node.js runtime or local HTTP server, and as the Driven SharePoint SSO/MFA adapter in `src/idat_sync/infrastructure/sharepoint_auth.py` behind a `WebViewDriver` protocol (`PyWebviewDriver` using a hidden window on Windows/macOS/Linux and `AndroidWebViewDriver` using an invisible `1x1` `android.webkit.WebView` with a standard `WebViewClient` and `CookieManager` via `pyjnius` on Android). Replacing Tkinter (`async-tkinter-loop`) and Playwright eliminates the ~50 MB Playwright Node driver and ~150 MB bundled browser binaries, removes the macOS PyInstaller `.framework` symlink repair script, avoids main-thread collisions between competing GUI event loops, works around `pywebview`'s Android single-window restriction and `PyWebViewClient.shouldInterceptRequest` HTTP POST body stripping, and enables a single UI and authentication codebase across Windows, macOS, Linux, and Android while keeping pure-Python UI component controllers (`MainApp`, `AppFrame`, `LoginFrame`, `SyncFrame`, `CourseTree`) unit-testable in memory without a display server.
